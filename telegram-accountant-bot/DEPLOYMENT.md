# راهنمای استقرار حسابیار (Technical Handoff)

سندِ فنی برای راه‌اندازی بات روی سرور. مخاطب: CTO / DevOps.

---

## ۱) در یک نگاه

- **زبان/استک:** Python 3.11، `python-telegram-bot` v21 (async)،
  **Google Sheets** به‌عنوان منبع داده (بدون دیتابیس محلی)، با یک لایه‌ی
  `Store` در حافظه که خواندن‌ها را از RAM سرو می‌کند و نوشتن‌ها را دسته‌ای
  (هر ۵ ثانیه) روی شیت می‌نویسد.
- **ورودی/خروجی:** فقط **long polling** به `api.telegram.org` — نیازی به
  دامنه، پورت باز یا وب‌هوک نیست.
- **نقطه‌ی اجرا:** `python -m hesabyar`
- **بدون state محلی:** یک فرایند کافی است؛ داده روی Google Sheets است.

> ⚠️ **مهم:** فرایند بات باید بتواند به `api.telegram.org` وصل شود. توصیه:
> سرور **خارج از ایران** (هم تلگرام هم سرویس‌های AI در دسترس‌اند). پرداخت
> کارت‌به‌کارت/زرین‌پال به موقعیت سرور وابسته نیست.

## ۳) شروع سریع (۵ دقیقه، با Docker)

```bash
git clone <REPO_URL> makair
cd makair
git checkout claude/telegram-accountant-bot-5xz3io
cd telegram-accountant-bot

cp .env.example .env
# فقط BOT_TOKEN را داخل .env بگذارید تا اولین اجرا انجام شود
nano .env

docker compose up -d --build
docker compose logs -f            # باید ببینید: «حسابیار در حال اجراست…»
```

همین. حالا در تلگرام به بات `/start` بدهید.

## ۴) اجرا بدون Docker (venv + systemd)

```bash
cd telegram-accountant-bot
python3.11 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env && nano .env
python -m hesabyar                 # اجرای دستی برای تست
```

سرویس دائمی با systemd (فایل آماده در `deploy/hesabyar.service`):

```bash
sudo cp deploy/hesabyar.service /etc/systemd/system/
# مسیرها و User را در فایل مطابق سرور خود ویرایش کنید
sudo systemctl daemon-reload
sudo systemctl enable --now hesabyar
sudo systemctl status hesabyar
journalctl -u hesabyar -f
```

## ۵) متغیرهای محیطی (.env)

| متغیر | پیش‌فرض | توضیح |
|---|---|---|
| `BOT_TOKEN` | — | **الزامی.** توکن بات تلگرام |
| `GOOGLE_SERVICE_ACCOUNT_JSON_B64` | — | **الزامی.** JSON کلید سرویس‌اکانت، base64 (`base64 -w0 key.json`) |
| `GOOGLE_SHEET_ID` | — | **الزامی.** شناسه‌ی اسپردشیتِ *مرکزی* (به سرویس‌اکانت Editor داده شود) |
| `DRIVE_PARENT_FOLDER_ID` | — | **الزامی در عمل.** پوشه‌ی Drive که شیتِ اختصاصیِ هر کاربر داخلش ساخته می‌شود. سرویس‌اکانت به‌تنهایی کوتای Drive ندارد؛ پوشه را با اکانت گوگلِ خودتان بسازید و با ایمیل سرویس‌اکانت **Editor** کنید. خالی بماند ⇒ ساختِ شیتِ کاربر با خطای کوتا شکست می‌خورد |
| `DEFAULT_CURRENCY` | `تومان` | واحد پول |
| `REMINDER_HOUR` / `REMINDER_MINUTE` | `9` / `0` | ساعت یادآوری روزانه‌ی سررسیدها (به وقت ایران) |
| `REMINDER_LEAD_DAYS` | `2` | چند روز قبل از سررسید هم پیشاپیش یادآوری شود (۰ = فقط روزِ سررسید و معوق) |
| `DAILY_SUMMARY` / `DAILY_SUMMARY_HOUR` | `true` / `22` | خلاصه‌ی خودکار آخر روز، فقط برای کاربرانِ فعالِ همان روز (نام‌های قدیمی `NIGHTLY_SUMMARY*` هم خوانده می‌شوند) |
| `ADMIN_IDS` | — | شناسه‌های عددی ادمین‌ها، با کاما. تأییدکننده‌ی پرداخت‌ها |
| `RATE_CHANNEL_ID` | — | کانالِ نرخ روزانه‌ی دلار (بات باید ادمینِ آن باشد). خالی = ثبت دستی با `/rate` |
| `PAYMENT_METHOD` | `card` | `card` (کارت‌به‌کارت) یا `zarinpal` (درگاه) |
| `CARD_NUMBER` / `CARD_HOLDER` | — | برای روش کارت‌به‌کارت |
| `ZARINPAL_MERCHANT_ID` | — | برای روش زرین‌پال |
| `ZARINPAL_SANDBOX` | `false` | حالت تست درگاه |
| `PAYMENT_CALLBACK_URL` | `https://t.me` | لازم نیست وب‌سرور بالا بیاورید؛ تأیید پرداخت با دکمه‌ی «بررسی پرداخت» انجام می‌شود |
| `TRIAL_DAYS` | `14` | طول دوره‌ی آزمایشی رایگان |
| `OCR_BASE_URL` / `OCR_API_KEY` / `OCR_MODEL` | — | سرویس تصویری برای خواندن عکس فاکتور (اختیاری) |
| `USE_LLM_PARSER` | `false` | استخراج هوشمند (نوع/دسته/فروشنده/تاریخ) با LLM |
| `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` | = مقادیر OCR | اگر خالی بماند از همان endpoint OCR استفاده می‌شود |
| `STT_BASE_URL` / `STT_API_KEY` / `STT_MODEL` / `STT_LANGUAGE` | = مقادیر OCR / `whisper-1` / `fa` | تبدیل ویس به متن (سازگار با Whisper)؛ خالی = fallback به OCR یا غیرفعال |
| `MOADIAN_BASE_URL` / `MOADIAN_TOKEN` | — | سامانه‌ی مودیان (فعلاً **اسکلت/dry-run**؛ ارسال گواهی‌شده پیاده نشده) |
| `SELLER_TIN` / `ECONOMIC_CODE` / `VAT_RATE` | — / — / `0.10` | اطلاعات مالیاتیِ فروشنده برای payload مودیان |
| `BACKUP_WEEKLY` | `true` | پشتیبان‌گیری هفتگی خودکار + اطلاع به ادمین‌ها |

> بدون `OCR_*`، خواندن عکس غیرفعال است ولی همه‌چیز دیگر کار می‌کند. بدون
> `USE_LLM_PARSER`، دسته‌بندی قاعده‌محور (کلیدواژه‌ای) کار می‌کند.

## ۶) داده روی Google Sheets

- **آماده‌سازی (یک‌بار):** پروژه‌ی Google Cloud با Sheets API + Drive API فعال؛
  یک Service Account با کلید JSON؛ یک اسپردشیت خالی که با ایمیل سرویس‌اکانت
  به‌عنوان **Editor** شیر شده باشد (`GOOGLE_SHEET_ID` را از URL آن بردارید)؛ و
  یک پوشه‌ی Drive که آن هم با سرویس‌اکانت Editor شده باشد
  (`DRIVE_PARENT_FOLDER_ID`).
- **یک اسپردشیت برای هر کسب‌وکار:** داده دو سطح دارد —
  - *مرکزی* (همان `GOOGLE_SHEET_ID`): `users`, `subscriptions`, `payments`,
    `rates`, `branches`, `branch_members`, `sequences`.
  - *اختصاصیِ هر کاربر* (خودکار در `DRIVE_PARENT_FOLDER_ID` ساخته و شناسه‌اش در
    ستون `sheet_id` جدولِ `users` ذخیره می‌شود): `transactions`,
    `ledger_entries`, `invoices`, `invoice_items`, `products`, `group_events`,
    `customers`.

  تب‌ها در اولین استفاده خودکار ساخته می‌شوند؛ شناسه‌ها از تبِ مرکزیِ
  `sequences` می‌آیند تا بین کاربرها یکتا بمانند.
- **ظاهرِ خودکار:** هر تب هنگام ساخته‌شدن یک‌بار استایل می‌خورد — هدرِ بولد و
  رنگی با ردیفِ فریزشده، جداکننده‌ی هزارگان روی ستون‌های پولی، و ستون‌های متنیِ
  پهن‌تر. چون `flush()` فقط مقدارِ سلول‌ها را بازنویسی می‌کند (نه فرمت را)،
  استایل برای همیشه می‌ماند و اجرای دوباره‌ی بات آن را تکرار نمی‌کند.
- **تبِ `📋 خلاصه` (فقط نمایشی):** یک نمای خوانا از مشخصاتِ کسب‌وکار و کالاها
  به تفکیکِ دسته. **بات هرگز از آن نمی‌خواند** — مدلی برایش وجود ندارد و
  `Store` تب‌ها را با نامِ مدل‌ها باز می‌کند. هر بار که کالا، پلن یا مشخصاتِ
  کسب‌وکار عوض شود از روی داده‌ی واقعی بازسازی می‌شود؛ پس اگر کاربر داخلش
  چیزی را دست بزند یا کلاً پاکش کند، هیچ داده‌ای از دست نمی‌رود.
- **در حافظه + نوشتن دسته‌ای:** اسپردشیت مرکزی هنگام بالا آمدن خوانده می‌شود و
  شیتِ هر کاربر در اولین تعاملش (lazy). خواندن‌ها از حافظه (سریع، بدون Rate
  Limit) و نوشتن‌ها هر ۵ ثانیه به‌صورت دسته‌ای روی شیت می‌روند. عملیات پول‌محور
  (تأیید پرداخت/صدور فاکتور) بلافاصله flush می‌شوند.
- **پشتیبان:** با `BACKUP_WEEKLY` هفتگی کل اسپردشیت به‌صورت اکسل برای ادمین‌ها
  ارسال می‌شود (Drive API). خودِ اسپردشیت هم History نسخه‌ی گوگل را دارد.

## ۷) سرویس‌های خارجی

- **خواندن فاکتور (OCR) و استخراج هوشمند (LLM):** یک endpoint سازگار با
  chat/completions نوع OpenAI (متن و تصویر). چون از داخل ایران محدود است،
  روی سرور خارج از ایران میزبانی یا پراکسی کنید و در `OCR_*`/`LLM_*` بگذارید.
- **تبدیل ویس به متن (STT):** یک endpoint سازگار با `audio/transcriptions`
  نوع OpenAI (مثل Whisper) که برای فارسی خوب کار می‌کند؛ در `STT_*` بگذارید
  (خالی = fallback به `OCR_*`). ربات‌های مصرفیِ ویس‌به‌متنِ تلگرام API ندارند و
  ارتباط بات‌به‌بات هم ممکن نیست، پس حتماً به یک API نیاز است.
- **پرداخت:** کارت‌به‌کارت (تأیید دستیِ ادمین با دکمه) یا زرین‌پال (کاربر
  لینک می‌گیرد، «بررسی پرداخت» را می‌زند، اشتراک خودکار فعال می‌شود). هیچ‌کدام
  به وب‌هوک یا وب‌سرور نیاز ندارند.
- **مودیان:** فعلاً اسکلت است و در نبود گواهی، حالت آزمایشی (dry-run) اجرا
  می‌شود. ارسال واقعی نیازمند کلید/گواهی رسمی و امضای دیجیتال است.

## ۸) کارهای زمان‌بندی‌شده (داخل خود فرایند)

با `JobQueue`ی `python-telegram-bot` اجرا می‌شوند؛ نیازی به cron جدا نیست:

- **`due_reminders`** — روزانه؛ یادآوری سررسید طلب/بدهی به کاربران، در سه بخش:
  معوق، سررسیدِ امروز، و نزدیک (`REMINDER_LEAD_DAYS` روز قبل).
- **`weekly_backup`** — هفتگی؛ کل اسپردشیت به‌صورت اکسل (Drive API export) برای
  ادمین‌ها ارسال می‌شود.
- **`daily_summary`** — هر شب (ساعتِ `DAILY_SUMMARY_HOUR`، پیش‌فرض ۲۲)؛ خلاصه‌ی
  فعالیتِ امروز + شمارِ موارد نزدیکِ سررسید، فقط برای کاربرانی که آن روز
  تراکنش، فاکتور یا ثبتِ دفتر داشته‌اند.

## ۹) امنیت و ملاحظات عملیاتی

- **اسرار** فقط از `.env` خوانده می‌شوند؛ در لاگ یا کد نیستند. `.env` را
  commit نکنید (در `.gitignore` هست).
- **SSRF:** خواندنِ فاکتور از «لینک» محافظت دارد — میزبان باید به IP عمومی
  برسد، ریدایرکت دنبال نمی‌شود، و سقف اندازه/زمان دارد.
- **منابع:** رندر داشبورد (matplotlib) و PDF فاکتور CPU-bound و کوتاه‌اند؛
  فایل‌های موقت پس از ارسال حذف می‌شوند.
- **تک‌فرایند:** با long polling فقط **یک** نمونه‌ی بات باید هم‌زمان اجرا شود
  (دو نمونه با یک توکن → تداخل getUpdates).
- **حالت گروه:** برای استفاده در گروه‌ها، در BotFather با `/setprivacy → Disable`
  حریمِ گروهِ بات را خاموش کنید تا بات همه‌ی پیام‌ها را ببیند و رویدادهای مالی را
  تشخیص دهد؛ وگرنه فقط پیام‌های ریپلای/منشن‌شده به دستش می‌رسد.

## ۱۱) مقیاس و محدودیت‌ها

- **تک‌فرایند/تک‌نمونه:** کل داده در حافظه‌ی یک فرایند نگه داشته می‌شود و همان
  فرایند صف نوشتن را روی شیت خالی می‌کند؛ پس باید فقط **یک نمونه** اجرا شود
  (روی Railway: `replicas = 1`). دو نمونه هم با polling تداخل getUpdates
  می‌سازند و هم صف نوشتن‌شان روی هم می‌ریزد.
- **سقف Google Sheets:** حدود ۱۰ میلیون سلول در هر اسپردشیت و محدودیت نرخِ API؛
  چون خواندن‌ها از حافظه‌اند و نوشتن‌ها دسته‌ای، برای ده‌ها/صدها کاربرِ فعال
  کافی است. برای مقیاس بسیار بالاتر، لایه‌ی `Store` را می‌توان بدون تغییرِ
  سرویس‌ها به یک دیتابیس واقعی (مثلاً Postgres) نگاشت.
- رندر داشبورد/فاکتور CPU-bound و کوتاه است؛ برای بار بالا می‌توان به یک
  worker جدا برد.

## ۱۲) استقرار روی Railway (سخت‌سازی)

Railway گزینه‌ی خوبی است چون سرورِ خارج از ایران می‌دهد و مستقیم از Dockerfile
build می‌کند. نکات مهم برای یک استقرار پایدار:

- **worker، نه وب‌سرویس.** بات فقط long polling می‌زند و هیچ پورتی گوش نمی‌دهد.
  نوع سرویس را **Worker** بگذارید (یا از `Procfile` با خط
  `worker: python -m hesabyar` استفاده کنید) تا Railway منتظر باز شدن پورت
  نماند و health-check نزند. `PORT` را ست نکنید.
- **`replicas = 1`.** فقط یک نمونه اجرا شود (بخش ۱۱)؛ مقیاس افقی این سرویس را
  روشن نکنید.
- **کلید سرویس‌اکانت را base64 بدهید.** JSON چندخطی در Variables خراب می‌شود؛
  با `base64 -w0 service-account.json` تک‌خطی‌اش کنید و در
  `GOOGLE_SERVICE_ACCOUNT_JSON_B64` بگذارید. مقدار واقعی کلید **هرگز** داخل
  کد/مخزن نرود — فقط از Variables.
- **خاموش‌شدنِ ایمن.** Railway هنگام deploy/restart سیگنال **SIGTERM** می‌فرستد.
  بات در `post_shutdown` صف نوشتن را با `await store.stop()` قطعی روی شیت
  می‌نویسد، پس داده‌ی در صف گم نمی‌شود. عملیات پول‌محور (تأیید پرداخت/صدور
  فاکتور) همان لحظه flush می‌شوند و منتظر تایمرِ ۵ثانیه‌ای نمی‌مانند.
- **راه‌اندازیِ مقاوم.** اگر اتصال اولیه به گوگل‌شیت برقرار نشود، بات با backoff
  تا ۵ بار تلاش و سپس با کد خطا خارج می‌شود تا Railway خودش restart کند
  (به‌جای بالا آمدنِ فرایندِ نیمه‌کاره). اگر نوشتن چند بار پشت‌سرهم شکست بخورد،
  به `ADMIN_IDS` هشدار می‌رود.
- **زمان.** `tzdata` در requirements هست تا روی image‌های slim منطقه‌ی زمانی
  درست کار کند.
- **لاگ‌ها.** همه‌ی لاگ‌ها به stdout می‌روند تا در پنل Railway دیده شوند؛ فایل
  لاگِ محلی نگه داشته نمی‌شود.

## ۱۳) عیب‌یابی رایج

| نشانه | علت/راه‌حل |
|---|---|
| بات جواب نمی‌دهد | دسترسی سرور به `api.telegram.org` را چک کنید؛ `BOT_TOKEN` درست باشد |
| `Conflict: terminated by other getUpdates` | دو نمونه‌ی هم‌زمان اجراست؛ فقط یکی را نگه دارید |
| در گروه، دستورها کار می‌کنند ولی پیام معمولی جواب نمی‌گیرد | Privacy Mode روشن است: BotFather → `/setprivacy` → **Disable**، سپس بات را از گروه حذف و دوباره اضافه کنید |
| خواندن عکس کار نمی‌کند | `OCR_*` تنظیم نشده یا endpoint از سرور در دسترس نیست |
| خطای build چرخ‌ها (wheel) | از image کامل `python:3.11` به‌جای `slim` استفاده کنید یا `build-essential`/`libffi`/`libfreetype6` را نصب کنید |
| بالا نیامدن با خطای گوگل‌شیت | `GOOGLE_SHEET_ID` و کلید سرویس‌اکانت را چک کنید؛ اسپردشیت باید با ایمیل سرویس‌اکانت **Editor** شده باشد و Sheets+Drive API فعال باشند |

| تغییرات روی شیت دیده نمی‌شود | نوشتن هر ۵ ثانیه دسته‌ای است؛ چند ثانیه صبر کنید. هنگام توقف، فرایند باید **SIGTERM** بگیرد تا صف قطعی خالی شود (نه `kill -9`) |
